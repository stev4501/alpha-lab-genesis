To write it honestly I read what the sealed code actually does rather than

`scripts/validate_repository.py`'s `VALIDITY_FIELDS` and `CORE_SKILLS`,
`schemas/experiment.schema.json`'s check enum, `loop/validate_session.sh`
checks 1 and 5, `CORE_MANIFEST.json`, `DATA_MANIFEST.json`'s dataset entries,
and `results/E-0002/validity.json`. Everything sealed was read, nothing was
written.

The core proposal: the five stamps stop being string literals and become
*derived* from an append-only check ledger built during the run and persisted
as `results/<E>/checks.json`. A check with no ledger entry yields `"not_run"`;
there is no code path that produces `"passed"` without evidence. And the
sealed validator gains the rule that makes it non-bypassable rather than
merely correct — for records at generation ≥ G-0004, any `"passed"` without a
matching ledger entry invalidates the repository contract, so hand-editing a
`validity.json` is caught by `loop/validate_session.sh` check 6 before
anything reaches `main`.

Per-check dispositions, argued from this data path rather than in general:
`lookahead_check` and `leakage_check` are genuinely implementable and should
read `"passed"`; `survivorship_check` is `"not_applicable"` and must not be
reachable as `"passed"` on a static one-symbol universe; `corporate_action_check`
must read `"not_run"` because the provider exposes no adjustment semantics
(this is B-0003); `missing_data_check` can only pass against a declared
expectation, for which I proposed an optional `expected_sessions` field in
`DATA_MANIFEST.json`.

On §1a I included the `CORE_SKILLS` un-hardcoding rather than deferring it,
because ADR-0008 records the human directing that the G-0004 proposal "must
also cover" it. The shape matters: derive the skill set from
`CORE_MANIFEST.json` (a protected file) and add a floor invariant requiring
the three operative skills, because un-hardcoding without a floor converts a
real constraint into no constraint at all.

On §8 I answered BL-0001's question: **record the interpreter version in
G-0004, do not enforce it.** Recording is two lines in a file already being
resealed, adds no invariant and no refusal path, and converts an
unfalsifiable determinism claim into a checkable one. Enforcement changes the
meaning of `design.environment_id`, reaches a second sealed script, and would
make every experiment unreproducible on a future runner image — it earns its
own request. I wrote the counter-argument against my own recommendation into
the document, because it is a real one: recording without enforcing means the
next replay mismatch is diagnosable but still happens.

## What surprised me

**Honest stamps make promotion impossible, and nobody had noticed.**
`scripts/finalize_experiment.py` lines 116–120 refuse to promote unless all
five checks read exactly `"passed"`. Two of the five cannot honestly read
`"passed"` here — survivorship is inapplicable on a one-symbol universe, and
corporate actions are unverifiable while the provider exposes no adjustment
metadata. So the fix to the stamps closes the promotion path until B-0003
resolves. I expected this change to be about honesty in a record; it turns out
to be about whether the system can promote anything at all.

The reassuring part is that nothing is lost: `STATE.json` records
`champion_strategy_id: null`, B-0001 and B-0003 are open and already say
historical strategy evaluation is not valid here, and the change would
therefore convert a narrative blocker into a machine-enforced one. That is the
whole point of the exercise, arriving from an unexpected direction. I
recommended leaving the gate strict and explicitly rejecting a per-experiment
waiver, on the grounds that a waiver is a bypass and this change exists to
delete a bypass.

**The migration can wedge the loop, and the agent cannot unwedge it.**
`loop/validate_session.sh` check 5 verifies sealed hashes on the session
branch against `CORE_MANIFEST.json` *at `REFERENCE_TAG`*. The instant a new
evaluator is on `main` with `REFERENCE_TAG` still at `pre-mvp-freeze`, every
session fails validation for a reason that has nothing to do with its work,
and gets quarantined to `failed/`. Both the tag variable and the manifest are
protected paths, so no session can repair it. §6a gives the required ordering.
Worth flagging for exit criterion 1: a session that fails during this window
is not evidence about the loop, and it is not criterion 2's induced failure
either.

**The golden replay test breaks under G-0004, in the quiet way.** It loads the
evaluator from the working tree (line 133) and asserts its hash equals the
G-0002 sealed hash (lines 188–201). The assertion failing is the good outcome;
the bad one is somebody deleting the assertion, after which the "replay of
E-0002" is silently running new code against old inputs. Yesterday's session
added that assertion precisely because "same evaluator" was otherwise an
assumption — one day later it is the thing that will catch this.

**A real defect fell out of drafting §3.1.** Line 417 is
`strategy(dict(history), date)`. `dict()` is a shallow copy, so the strategy
receives the evaluator's own row lists and its own mutable row dicts. It
cannot see the future through them, but it can rewrite the past mid-run and
nothing would detect it. Small, real, and exactly the kind of thing a
lookahead check should close. I folded it into the invariant rather than
raising it separately: G-0004 is the only generation bump on the table, and a
second request for one line would cost a second approval round trip and a
second freeze tag.

**Also noted, not acted on:** D-0001, D-0002, and U-0001 all read
`"status": "unverified"` in `DATA_MANIFEST.json` today, and the evaluator
refuses to run without a `"validated"` dataset and universe (lines 335–337).
No new experiment can be evaluated on this repository right now regardless of
G-0004. That is consistent with B-0001/B-0003 being open, and it means the §5
tests will need a scratch manifest rather than the live one.

  produced the `additionalProperties: false` constraint, which is the reason

- I revised §3.6's recommendation after first drafting it: "(a) plus (b)" was
  ambiguous, since (a) is "leave the gate strict" and (b) modifies the gate.
  It now names the concrete rule — a check passes if it is `"passed"` or
