## What surprised me

**The promotion gate is the interesting half of this defect, and the backlog
item pointed at the other half.** BL-0002 frames the defect as "five stamps are
unearned" — true, and the framing everyone has carried since ADR-0008. But an
unearned `"passed"` is only half a bug. The other half is that
`finalize_experiment.py` already refuses to promote unless all five say
`"passed"`, which means the system already has the enforcement it needs and the
evaluator is the thing lying to it. The gate is not missing. It is being fed.

That reframes what G-0004 has to buy. It is not "add enforcement"; it is
"stop manufacturing the input the enforcement consumes", and then — necessarily,
in the same breath — teach the gate the difference between "this check ran and
passed", "this check cannot apply to a one-symbol universe", and "this check has
not been implemented". Without that distinction the honest system is strictly
less capable than the dishonest one, because nothing can ever be promoted. I do
not think that consequence has been written down anywhere before now, and it is
the reason this request is larger than a one-line change to a dictionary
literal.

**Second: yesterday's deliverable is today's migration cost.** BL-0001's golden
replay, written 2.5 hours ago, breaks under G-0004 at two specific assertions,
by construction and correctly. `test_evaluator_bytes_are_the_sealed_g0002_evaluator`
(line 188) asserts the on-disk evaluator's sha256 equals the sha256 recorded for
it in the G-0002 manifest — G-0004 changes those bytes. And
`test_replayed_outputs_are_byte_identical` (line 221) compares `validity.json`
byte-for-byte against E-0002's recorded all-`passed` file, which an honest
evaluator will no longer reproduce.

Neither is a defect in the test. But it means "land G-0004" is not a change to
sealed files plus a manifest — it silently includes rewriting a test in `tests/`,
and whoever applies it would otherwise discover that from a red suite after the
seal was already broken. I wrote the rewrite into the request as a required part
of the same landing: replay against the G-0002 evaluator bytes read from git at
`design.code_commit`, rather than against whatever is on disk. That is what
"golden replay" should have meant from the start, and it makes the test immune to
every future generation instead of exactly one.

**Third: a silent trap in the artifact plumbing.** I had written that
`checks.json` could be "appended to the `outputs` list" and the artifact manifest
would pick it up for free. That is wrong in a way that produces no error. The
manifest loop iterates `outputs[:-1]` (line 476) because the last element is
`artifact-manifest.json`, which cannot hash itself. Appending `checks.json` after
it would leave the file written to disk, unhashed, absent from the artifact
manifest, and therefore absent from the `EXPERIMENTS.jsonl` artifact list — which
is exactly the evidence the new validator invariant depends on. The whole
integrity chain would be one list position away from being decorative, with
nothing anywhere reporting a problem. It is now named in the request as a trap
and folded into a test.

Fourth, smaller: `evaluator/daily_bar.py` builds `validity` as
`{**prereg["validity"], <five overrides>}` (lines 429–437). The preregistered
values are all `"not_run"` (`scripts/preregister_experiment.py` lines 149–153).
So the correct G-0004 behavior for an unimplemented check is *already* what the
preregistration says — deleting the five override lines and writing nothing in
their place would produce honest `"not_run"` stamps. The minimum honest fix is
a deletion, not an addition. Everything beyond that deletion exists to let a
check that does run say so credibly.

## Notes for whoever runs next

- The request names its own successor freeze tag `pre-g0004-freeze` and states
  why the name matters: the ruleset pattern is `refs/tags/pre-*`, so a tag named
  outside it is created successfully and protected by nothing, silently. That
  trap is BL-0002 item 6a's, not mine, but the request now carries a
  verification step (attempt a force-update, expect rejection) so it cannot be
  assumed.
- `scripts/validate_repository.py` verifies sealed hashes against the
  `CORE_MANIFEST.json` in the working tree (line 387), while
  `loop/validate_session.sh` verifies them against the manifest as it exists at
  `REFERENCE_TAG` (line 16). A G-0004 that reseals hashes passes the first the
  moment the manifest is updated and fails the second until the tag variable
  moves. Whoever applies G-0004 should expect the session validator to go red
  in exactly that window, and should not "fix" it by editing hashes.
